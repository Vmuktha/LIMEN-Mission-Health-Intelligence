# Data provenance

LIMEN separates the following categories of information.

1. **Published astronaut research**: study descriptions and findings, preserved as citations in `SCIENTIFIC_EVIDENCE.md`. These are not re-labeled as LIMEN observations.
2. **User-generated browser assessment measurements**: completed browser assessment sessions may be persisted locally in the browser's IndexedDB database. They retain their original trial records, timestamps, phase/rotation conditions, missing values, and already-derived summaries. No server database, authentication, cloud synchronization, or external data import is part of this phase.
3. **User-generated sensorimotor check-ins**: optional 0–10 self-reports of dizziness/disorientation, balance or coordination difficulty, nausea, visual discomfort, fatigue, and movement confidence. These remain subjective self-reports and are not objective sensor, vestibular, neurological, or medical measurements. Unanswered fields remain absent, never zero.
4. **Simulated mission demonstration data**: optional illustrative records used only to explain a future interface. They must be visibly labeled simulated at every appearance and must never be mixed with user-generated data.
5. **User-recorded mission context and workflow records**: mission contexts, mission events, and follow-up records entered in this browser profile. A mission phase is only the value explicitly recorded by a user; it is never derived from a timestamp or schedule. Follow-up records are administrative workflow notes, not medical advice or a LIMEN escalation.
6. **NASA OSDR reference measurement data**: transformed, study-level biospecimen measurements published by NASA OSDR under CC0 1.0. These are reference observations about four Inspiration4 crew members, not telemetry, not LIMEN records, and not joined to any browser assessment, check-in, mission event, or follow-up.

Records are written with duplicate-safe identifiers and can be deleted through the future local-data controls that call the storage deletion functions. Browser IndexedDB is device/browser-profile local: clearing site data, using private browsing, browser policy, storage eviction, or changing devices may remove or isolate records. No astronaut-level raw data is bundled, fetched, or fabricated. Data export, retention, consent, access controls, and operational deployment requirements are outside this prototype phase and require separate governance.

Pre-assessment check-ins are deliberately not linked to an assessment-session identifier: a real session has not been created at that stage, and LIMEN does not fabricate one. A post-assessment check-in may include the identifier of the actual completed browser session. The results view distinguishes direct browser records (trials and timestamps) from derived descriptive metrics and self-reports; it does not infer change, recovery, or clinical status from either category.

Assessment records created before protocol v0.2.0 did not capture an actual pointer origin before target presentation. LIMEN preserves those browser-local records unchanged as `legacy-origin-unverified`; it does not rewrite, delete, or recalculate them. Corrected v0.2.0 records include a captured actual start and positioning timestamp. Legacy and corrected records are not pooled in phase, adaptation, or aftereffect summaries, and any collection mixing measurement protocol versions withholds pooled timing as well as origin-sensitive metrics.

Protocol v0.3.0 adds a measurement-protocol change: the native browser pointer is hidden during active interaction, while pointer capture, positioning, target geometry, and timing rules remain the same as v0.2.0. New records use the per-trial measurement label `0.3.0-actual-pointer-origin-hidden-cursor`. Historical v0.2.0 sessions are not migrated or rewritten; they remain `0.2.0-actual-pointer-origin` and are retained unchanged. Both versions are origin-corrected, but they are distinct measurement protocols: a trial collection containing more than one measurement protocol version is never treated as a homogeneous comparable group, and pooled directional, trajectory, correction, adaptation, washout, reaction-time, and movement-time summaries are withheld rather than silently merged. Direct comparison requires two verified-origin trials with the same explicit measurement version. The stored session protocol version is cross-checked against trial-level measurement versions; missing, unknown, or inconsistent labels are handled conservatively. Historical trials without a per-trial label are treated as legacy only when the stored session itself identifies protocol v0.1.0; unversioned trials are never upgraded to corrected origin. Homogeneous legacy sessions retain valid reaction and movement times. Derived summaries may be recomputed from raw trials at display or analysis time without modifying stored records. Empty record sets are reported as `no-trials` rather than legacy, and records whose actual start is missing, non-finite, or lacks a positioning timestamp are never labelled verified-origin.

The legacy-compatible non-positioning engine path records `0.1.0-legacy-origin-unverified` and omits both the captured actual start and the positioning timestamp. This prevents a trial from inheriting a verified-origin label merely because it ran through the same engine.

## Recovery data provenance

Phase 7A derives recovery observations from already-stored browser records; it does not create a new source of truth. `buildRecoveryDataset()` is pure, and `loadRecoveryDataset()` reads through the existing `listAssessmentSessions()` and `listCheckIns()` storage APIs. The dataset preserves each observation's session ID, participant ID, original completion and recording timestamps, assessment protocol version, measurement protocol version(s), input device, and browser-generated provenance. Stored sessions and check-ins are never mutated.

Only completed assessment sessions enter recovery observations. Sessions are sorted by `metadata.completedAt`, not by IndexedDB `getAll()` order. Incomplete, aborted, or missing/invalid completion timestamps are exposed in `excludedSessions` with a reason. Malformed, simulated, non-browser, or structurally invalid records are exposed in `rejectedRecords` rather than silently dropped. Trials are validated defensively: the parent session ID must match, coordinates and timestamps must be finite, outcomes and phases must be recognized, and trajectory samples must be finite and non-negative. Non-finite measurements are withheld; they are never replaced with zero. Timing metrics can remain available when only origin provenance is compromised, but origin-sensitive metrics are withheld.

All metrics are recomputed from the raw trial records. Stored phase summaries, adaptation summaries, and baseline comparisons are not trusted as recovery inputs. The measurement-validity layer from Phase 7.0.1 supplies the protocol gate: homogeneous legacy sessions may retain timing metrics; origin-sensitive metrics require a homogeneous corrected protocol with verified actual-pointer origins; mixed, unknown, or inconsistent protocols withhold pooled metrics. v0.2.0 and v0.3.0 remain distinct measurement protocols and are never pooled.

The single browser-local participant profile remains the only identity boundary. Participant grouping uses the existing participant ID; it does not create accounts, verify a human identity, or support multi-participant management. Check-in associations use only an explicit `assessmentSessionId` that points to a valid completed session for the same participant. Timestamp proximity is never used to infer a relationship. Check-ins without an explicit identifier, with a missing session, with an incomplete session, or with a participant mismatch remain unassociated and retain an explanation. Unanswered self-report scores remain null.

Derived recovery values are descriptive analysis products, not new measurements or clinical evidence. A Personal Reference Session is selected from eligible completed observations, defaults to the earliest eligible session for the relevant metric, and is never automatically the best or most recent session. An explicit override is validated for participant, metric eligibility, and protocol compatibility. Metric deltas are `currentValue − referenceValue` and remain descriptive; they are not diagnostic, fitness-for-duty, or recovery determinations.

### Dashboard provenance

The `/recovery` dashboard is a read-only presentation layer. Its client-side hook calls the existing `loadRecoveryDataset()` once per mount and builds a pure dashboard model from the returned dataset. It never writes to IndexedDB, rewrites historical sessions or check-ins, or creates replacement records. Loading, empty, and error states are displayed explicitly, and an empty profile is never filled with simulated observations.

The dashboard does not create a second source of truth. Reference selections and observation choices exist only in component state; they are not persisted into historical assessment records. Automatic references are recomputed per metric at display time. Explicit references remain validated by the Phase 7A rules and are never silently replaced.

Trend series are derived from eligible metric values in the recovery dataset. Each measurement protocol is drawn separately, and missing values break the series rather than becoming zero or interpolated points. The charts are visual guides, not additional measurements.

Performance–self-report alignment uses only check-ins that already carry an explicit `assessmentSessionId` pointing to the relevant completed current or reference session, and only those with `post-assessment` context. The dashboard preserves null answers, displays multiple check-ins individually, and counts excluded check-ins. It never searches for a nearby timestamp to construct an association and never infers causation from co-observation.

### Display provenance

Recovery timestamps are rendered in UTC and labelled as such, so a stored record reads identically for every reader regardless of local timezone. Metric values are displayed with the unit stated once per metric instead of being repeated inside each number, which keeps a signed difference from being read as a labelled judgement.

The dashboard resolves a single browser-local participant profile. The established `browser-participant` identifier is preferred; otherwise exactly one profile with completed observations is used. Profiles are never merged, and a check-in-only profile never removes an observation-bearing profile from view. If several observation-bearing profiles exist, the dashboard reports the ambiguity instead of choosing between them, because the prototype provides no multi-participant management. Reference selection, the observation under review, and the focused metric exist only in component state and are never written into historical records.

## Stage 4 provenance

Stage 4 adds a typed domain layer without creating a new source of observational truth.

- **Expanded check-ins** keep the original six self-report items and add `sleepQuality`, `sleepScheduleDisruption`, `workload`, `stress`, `generalWellbeing`, and `existingSymptoms`. Every item declares its polarity; opposite-polarity answers are never averaged. An omitted item remains absent, never zero. A free-text note is optional, trimmed, locally stored, bounded at 1,000 characters, and is not analysed or transmitted. A stored check-in may name an explicit `assessmentSessionId`, `missionContextId`, and `missionPhase`; none is inferred.
- **Mission contexts and events** are user-entered records with an explicit source and provenance. An event's `occurredAt` is never used to derive its phase. The three legacy phase values (`inflight`, `postflight`, `reconditioning`) remain readable in stored records but are not accepted for new mission-context creation or phase changes.
- **Signal Concordance** is a pure derived result. It is not persisted, does not create a new observation, and uses only explicitly supplied session and check-in identifiers. It never selects a check-in by timestamp proximity, never pools measurement protocol v0.2.0 with v0.3.0, and never produces a composite, readiness, risk, causal, or predictive statement.
- **Follow-up records** are user-entered administrative workflow records. A referral is a request that an authorised reviewer consider an observation; `performedByLimen` is always `false`. LIMEN does not diagnose, prescribe, contact a clinician, or transmit records.
- **Evidence intelligence** keeps five categories structurally distinct: published research findings, NASA study-catalogue metadata, downloadable NASA measurement data, user-generated observations, and synthetic demonstration scenarios. Only a measurement-data record exposes source files. A catalogue record is never presented as a downloadable dataset, and no publication, finding, participant measurement, or availability status is fabricated.
- **OSDR timelines** are pure access functions over the existing typed datasets. Serum and whole-blood series remain distinct, missing tokens remain missing, and source reference ranges are carried without evaluation. No OSDR measurement is joined to a browser record.

### Persistence provenance

The IndexedDB database `limen-neuroadaptive` is upgraded additively from version 1 to version 2. The original `assessment-sessions` and `sensorimotor-checkins` stores are preserved unchanged; `mission-contexts`, `mission-events`, and `follow-up-records` are created only if missing. No store is deleted or recreated. Inserts are duplicate-safe, and updates use explicit `replace*` functions after domain validation. Simulated-demo records are rejected by real stores. There is no backend, account, network service, or cross-device synchronization; records remain local to the browser profile and are subject to its storage policy and eviction.
